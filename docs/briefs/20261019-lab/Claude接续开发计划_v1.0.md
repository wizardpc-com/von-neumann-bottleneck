# 《冯·诺依曼瓶颈》Claude 接续开发计划 v1.0

**执行窗口：2026 年 10 月 19 日起的这一轮夜间开发**  
**对象：Claude / Opus 主开发线程**  
**性质：可执行的产品与开发任务书，而非仅供讨论的策划提纲**

> **本轮目标：** 在现有可玩系统之上，把分散的关卡、界面、引导与成果组织成一款真正有空间、有氛围、有操作乐趣的游戏。今晚必须产生实际可运行的变化，不只是方案、注释、验证记录或更多功能入口。
>
> **首要体验：** 进入温润的未来实验室 → 看到并操作深色终端 → 开始构建 → 看懂真实结果 → 得到有感染力但克制的反馈 → 自然进入下一段旅程。

## 01｜先统一对项目的理解

### 游戏到底要呈现什么

- **游戏首先是构建与解谜。** 玩家不是阅读计算机教材，而是亲手连接、试验、优化与创造，由操作理解规则。
- **实验室是承载这一旅程的世界空间。** 它应是封闭、尺度适中、明亮温润、有人维护的未来实验室；外部空间以灰白、浅蓝为主。实验室里有一台视觉上明确的深色计算终端或实验台。
- **终端是实际操作入口。** 终端界面偏深灰、蓝灰与柔和青色，像真实研究仪器，避免把大量系统窗口直接堆在玩家面前。
- **空间可以看、可以有限地转动视角，但暂不需要自由行走。** 真正需要交互的是菜单、终端与谜题，而不是复杂的第一人称探索。
- **壹仍然存在，并正尝试逐渐退出神明式的主导地位。** 玩家在学习程序中理解系统、发现历史，最终走向自己的判断与创造。玩家并非预设的“天选救世主”。主旨延续 **A Thought Within the World**。
- **故事应贯穿游戏，而非只在片头出现。** 引导、关卡中间的发现、成果反馈、档案与最终作品彼此关联；弥拉、神像、议事厅等仍为团队故事候选，不能自动定为正史。

### 不要延续上一轮的偏差

已有系统完成了不少工程工作，但**工程验证通过不等于主创认可的游戏体验成立**。这一轮要敢于整理、合并、重新布局和改写玩家可见的部分，不能只做更深的说明层、更多弹窗和导航捷径。不要为了维持旧页面而回避真正的交互问题。

建议用三个判断衡量每一项改动：

1. 玩家**看到了什么变化**？
2. 玩家**能够更自然地完成什么操作**？
3. 这项变化是否让游戏**更有趣、更清楚或更连贯**？

## 03｜今晚的开发顺序

下面是**优先顺序**，不是要求一口气做完所有页面。每一轮都要有可运行成果；如果某项设计尚缺素材，就先用合适的临时内容继续开发。

| 轮次 | Claude 需要推进的内容 | 这一轮应该交付什么 |
| --- | --- | --- |
| **R0 · 接续与体验诊断** | 检查真实工作区、交接、当前游戏运行；亲自审阅首页、序章、一处中期关卡和 C/P/G 的画面与操作；区分已有、问题和可重用部分。 | 简短问题优先级；可靠的可运行起点；真实现状截图。不要停留在长篇审计。 |
| **R1 · 实验室首页与终端入口（最高）** | 把首页从独立菜单/抽象3D观察页改成**实验室场景式入口**。实验室明亮、温润、封闭适中；终端深色、成为视觉焦点。玩家从这里进入、继续、返回与打开必要功能。 | 可启动、可点、可返回的首页候选，至少一张真实运行截图及可演示的切换；临时美术也可以。 |
| **R2 · 首次完整体验（最高）** | 衔接“进入终端 → 壹的简短引导 → 真实操作/NOT教程 → 运行和判断 → 有感的首次反馈 → 继续下一项”。减少割裂窗口和长段说明。 | 一段能从新档实际玩通的完整旅程；操作/结果/反馈连续；保留可跳过、恢复和重看。 |
| **R3 · 全游戏重点优化（重要）** | 用统一标准检查全旅程，实际改进一组有代表性的中期关卡、另一组后期内容，重点是布局、任务目标、运行可视化、反馈和章节衔接。 | 至少两处来自不同系统的真正可用改进，附前后画面或操作差异；其他章节给出轻量待办。 |
| **R4 · 新内容与叙事表现（有余力继续）** | 在已经能玩的路径上加入**有意义的新体验**，例如可探索的档案片段、一次成果引起的环境回应、与真实计算绑定的短挑战或新的历史发现。优先选择可以自然服务主旨、与现有系统相连的内容。 | 至少一项完整候选，而非纯文字设想。故事未定稿的部分可替换，独立于核心通关。 |
| **R5 · 统一审阅与交接** | 运行必要测试，实际检查关键窗口/录屏/截图，修复明显破坏体验的问题，整理可交给队友接续的接口。 | 可玩候选版本、最重要的变化对照、已修复/待做清单、明确的素材需求与下一轮优先级。 |

**实际推进原则：R1/R2 是产品主轴，R3 是防止“只做好首页”的必要扩展。** R4 不应挤掉前面几轮的整合与测试；但如果前面完成得快，不要在汇报后停机，继续开发下一项有价值的内容。

## 04｜实验室首页：具体想要的形态

### 首页目标画面

玩家第一次打开游戏，看到的是**一个小而真实的未来实验室**，而非宏伟空旷的展馆，也不是直接贴在插画上的传统菜单。场景里有一台明显可交互的深色终端，实验室的柔和环境光与终端屏幕形成自然对比。

建议体验：

**实验室待机全景 → 轻微转头或视角响应 → 终端被选中并亮起 → 菜单/启动操作 → 镜头轻推或柔和过渡 → 真实的2D计算工作台。**

首页不必承载完整世界观CG。只需让玩家感到“我进入了什么地方”“眼前最重要的设备是什么”“我现在可以开始做什么”。操作台可以有开始、继续、任务/旅程、设置、退出等必要入口；具体位置与表现由实际样稿决定。菜单始终清晰可点，不用强迫玩家在房间内走路找按钮。

### 表现技术由实际效果选择

请 Claude 在真实开发环境里快速比较两条路径，不要先押注某个工具：

- **有限视差/预渲染2.5D：** 用 Blender 或现有图像素材提供空间、光影和激活状态，Godot 负责菜单、切换和动态交互。适合固定构图、轻微视差。**单张底图不能实现真正的立体转头**。
- **受限镜头的轻量3D：** 场景简单、机位固定，摄像机只允许小范围转向/观察，终端仍接原2D工作台。适合确实需要“可以转头”的体验，但要求真实渲染、输入和性能验收。

允许采用混合方案，或者先做一个预渲染可交付首页，同时保留简短的3D比较原型。**今晚不用追求大规模高精度建模。** 用户与陈梓弘将继续制作或筛选正式场景、终端与图标素材；Claude 先稳定构图、交互和可替换位置。

| **展示与发布** | 为真实玩法录制/截取留出稳定入口；修开发入口与版本辨识，整理新版本可用素材。 | 苏子航负责PPT和展示，罗雅琪负责对应故事镜头；赛前完成一致的游戏包、实机画面与展示材料。 |

### “新内容”怎样选，避免只堆功能

优先选择**玩家确实能够做或发现的新事情**，而不是一个额外的窗口或技术报告。候选例子：

- 第一次正确完成某项构建后，实验室里有一处简短、可回看的环境回应，随后开启一条与这项能力相关的档案线索。
- 中期第一次测到“快CPU仍在等数据”时，利用真实图表和控制实验引出一段更深的探索，不只是多一段文字。
- 压缩／预测／创造之间，让玩家清楚地拿前一步的结果继续下一步，并保留属于自己的创作成果。

选择一项深入做通，比同时增加三个缺乏整合的新入口更有价值。若要新增正式关卡，需要先核对真实模型、目录、存档与任务契约；**不为演出效果编造模拟成绩**。

## 07｜每轮怎样工作与交付

采用“**观察真实问题 → 提出最小可试的改法 → 真正写进游戏 → 截图/试玩 → 继续调整**”的连续循环。

- **一轮一个主要体验主题。** 可并行准备互不冲突的文字、素材、脚本，但共享 UI/场景由主开发线程统一集成。
- **先动手、再复盘。** 简短列出准备改什么即可启动，不需要先写另一份长长的分析报告。涉及跨系统修改时按仓库 `PLANS.md` 留必要计划。
- **每轮都展示证据。** 至少展示实际运行的前后画面、真实交互路径或可查看样例，附关键修改文件与测试结果；不把概念图称为游戏实机画面。
- **先修看得见的问题。** 如果出现明显挡按钮、镜头不舒服、终端不可点、操作不明白，优先改它们；不要先对无关测试扩写十几页文档。
- **交付可恢复。** 检查源文件、真实进度与存档；遵守 `AGENTS.md` 的 Git 权限与工作树协作约定。避免与其他代理同时争用同一批文件。
- **仅把需要创意裁决的大问题交给严睿清。** 局部排版、过渡节奏、可替换的普通文案由 Claude 自主试验；未确定的核心角色形象、主线结局、美术最终定稿交团队讨论。

### 今晚的最低成功标准

在已有工作量允许的情况下，至少交付：

1. **可用的正确开发入口**，让主创清楚地在源工程看到候选完整旅程，且正常/测试者进度不混淆。
2. **一个能真实交互的实验室式首页候选**，能进入现有终端/关卡并返回。若真实3D尚不足以采用，也须提供有操作闭环的高质量替代版本，而不只是一张图。
3. **一段由新档实际操作到首次反馈的体验**，包括必要引导和清楚的结果，不以测试脚本替代玩家路径。
4. **跨章节的实际改进**，至少一处中期和一处后期优先问题得到可运行修改或明确的局部完成证据。
5. **可审阅的交接物**：最重要的实际截图/短演示、变化摘要、同学可接续的美术/文案/镜头接口和下一轮顺序。

这不是要求一晚做出正式CG、完整3D世界或60关全部改版。优先确保前四项有明确进展，剩余问题实事求是留下，不要以重复验证或新增空白入口充当产品进展。
