## 1. 产品定位与核心体验

### 1.1 一句话定位

> **一款围绕计算机数据流的构建与优化解谜游戏：把机器接通，让它正确工作，再改变数据怎么走、什么时候用、留在哪里，使它少等一点。**

首先是一款游戏；学习价值由可观察、可操作、可迁移的因果关系产生。不要把 Demo 做成实验报告生成器、体系结构知识清单或模型评测平台。

### 1.2 核心循环

**接到具体任务 → 看清规则与当前机器 → 提出想法 → 改动一个方案 → 运行 → 从结果与数据流理解效果 → 继续改进。**

这是一条玩家思考路径，不是七个必须逐项点击的流程状态。游戏应提供比较和证据，不要求玩家每次填写“猜想”和“结论”。

### 1.3 必须交付的三次认识转变

| 认识转变 | 玩家操作 | 可见证据 |
|---|---|---|
| 计算快了，整机却未明显快起来 | 更换 CPU，比较同一任务 | 计算缩短，等待基本不变 |
| 装上缓存，仍可能更慢 | 查看访问顺序并重排程序 | 同一缓存行在使用完前被换走；重排后远取减少 |
| 不一定要买更大缓存 | 改变分组与复用时机 | 小缓存也能避免重复搬运；速度和成本可以权衡 |

### 1.4 与 Turing Complete 的边界

Turing Complete 官方路线包括从逻辑门到组件、存储、计算机架构，再在自建硬件上编程。[W1] 本作借鉴直接操作、组件可读性和成果复用，但不复制其完整知识前置。

本作的主要成长是“我让机器少等了，而且知道为什么”，不是“我又重建了一个更复杂的逻辑组件”。不能用“图灵完备只搭建，本作才优化”作不准确的竞品区分。

**主线保留：** 输入/输出、数据与控制、位宽、MUX 选择、写入/保持、地址、LOAD/STORE、等待、延迟与传输、缓存、访问顺序、工作集和分块。

**可选深入：** 半加器、全加器、完整多运算 ALU、NOR 锁存、SR→D、RAM 内部拼装、完整小 CPU 布线。

## 2. 证据与优秀游戏经验：转成实施规则

### 2.1 不能被新文案掩盖的试玩信号

[F1] 中前七关合计约 33.8 分钟，计入 CPU 退出前约 39.5 分钟；ALU 正式运行一次通过，但有趣程度和继续意愿均为 1/5；CPU 使用 5 次提示、最高到第三级，仍在 0 次正式运行后退出。

这些事实支持三个方向：主题不能出现太晚；通关率不能代替有趣程度；信息缺失不能充当难度。Half Adder 的 42 次修改本身不能证明 Bug，必须结合“选不中、拖不动”等口述解释。

上一轮已加入元件说明、opcode 表、阶段提示及多项交互修复。[A1][R6] 本轮应检查它们是否可用、是否清晰，而不是把它们再次当作不存在的功能重写。

### 2.2 经验来源与具体落地

| 外部依据 | 来源实际支持的经验 | 本作采用方式 | 不照搬的部分 |
|---|---|---|---|
| Turing Complete 官方介绍 [W1] | 从基本组件逐步构成更高层结构 | 小任务建立可复用概念，成品能够继续使用 | 不把完整门级路线设为性能主题的入场考试 |
| Opus Magnum 官方介绍 [W2] | 开放解法，比较简单、快速、紧凑等不同方向 | 先有可接受解，再给成本/速度的可选优化目标；保留个人最佳 | 不复制炼金主题、美术、排行榜或分享平台 |
| SHENZHEN I/O 官方介绍 [W3] | 电路、代码、元件规格和工作情境结合 | 一句真实委托＋清楚规格，技术解释放在需要的位置 | 不复制长手册门槛和大量角色系统 |
| Portal 开发负责人 Kim Swift 的直接访谈 [W4] | 从开发早期持续试玩，把新关卡和说明尽快放入游戏检查 | 先做可玩的核心短切片，再推广到全 Demo | 不把大型团队的测试频率当作单人硬性排期 |
| Schell Games 试玩说明 [W5] | 试玩用于找体验的问题，不是考玩家能力 | 记录卡点与误解；不要用开发者口头讲解抵消缺失的游戏信息 | 不因玩家没读懂就判定“目标人群不对” |

**以下是由这些参照和本项目证据形成的设计建议，不是上述作品的逐字规则：**

- 一个主要认知目标可以在同一关内经历发现、试验和改进，不必拆成三个节点。
- 重复动作只有在约束、观察结果或推理关系变化时，才值得再次出现。
- 反馈应说明“发生了什么”，而不是替玩家宣布“你已经理解了什么”。
- 首次方案可行后应保留再优化空间，不能自动跳关打断兴趣。
- 先证明一段核心体验值得玩，再把共享 UI 和内容结构推广；不要先造通用游戏框架。

## 3. 新路线：8 个主线节点＋可选硬件工坊

### 3.1 主线路线图

```text
序章：让机器工作
P-1 接通第一台机器
  ↓
P-2 把结果留住
  ↓
第一章：机器为什么在等
1-1 换了 CPU，为什么还慢
  ↓
1-2 钱该花在哪里
  ↓
第二章：少搬一点数据
2-1 别再跑远路
  ↓
2-2 换个读取顺序
  ↓
2-3 这一小块，先做完
  ↓
2-4 最后一单
```

默认“开始游戏”进入主线，不再让新人在三个原型入口中选择。保留“继续游戏”和次级“硬件工坊”。地图展示当前任务和近邻目标，不先塞满未来全部术语。

### 3.2 节奏预算

| 节点 | 新的主要认知 | 主体验预算 | 本关新增的操作负担 |
|---|---|---:|---|
| P-1 | 来源选择、连接与输出 | 5–7 分钟 | 必要接线、选中、撤销、运行 |
| P-2 | 状态，再到地址化读写 | 5–7 分钟 | 逐阶段增加，不同时教完整控制器 |
| 1-1 | 计算与等待的区别 | 6–8 分钟 | 替换一个部件、看前后变化 |
| 1-2 | RAM 服务与总线传输不同 | 7–10 分钟 | 比较不同机器条件下的改动 |
| 2-1 | 第一次取回、后续复用 | 6–9 分钟 | 启用缓存，跟一次关键往返 |
| 2-2 | 内存布局与访问顺序 | 8–12 分钟 | 小程序重排，先不增加硬件维度 |
| 2-3 | 容量与复用间隔 | 8–12 分钟 | 分组安排，观察两轮顺序 |
| 2-4 | 已学机制的组合与权衡 | 12–18 分钟 | 不增加新规则或语法 |

这些区间合计约 57–83 分钟，可把初版完整主体验设为约 60–90 分钟的验证目标。它不是必须凑满的时长。工坊、阅读手册和深度优化另计。

首个可理解行动尽量在开场 2 分钟内出现；首次瓶颈相关决策争取在约 10–15 分钟开始。基础两关超预算时，减少必做内部构建，不能通过压缩字号或增加操作指引硬塞。

### 3.3 可选硬件工坊

工坊继续复用现有算术/存储双分支及完整 CPU 集成。玩家可以从主线遇到的 MUX、寄存器、RAM 查看“它内部怎样工作”，但不弹窗强迫离开主线。

工坊内部可以有必要的依赖；已有知识的玩家可以跳过教学说明，但不能伪造已验证的自建成果。正常主线始终有合法标准组件，不依赖 Test 模式临时库。

工坊贡献的是深入理解和构建成就。**当前性能模型不从门级实现推导速度，因此不能宣传“门数更少，主线 CPU 就自动更快”。**

## 4. 八个主线任务的可执行设计卡

本节是对已认可路线的实施细化。具体数据、性能门槛和可用零件须由当前引擎验证，不准把下述示例直接当作已存在关卡。

### P-1 接通第一台机器

**任务：** 按控制信号，从两个数据来源中选出本次要用的值，并把它送到结果端。

**供给：** 少量输入、数据选择模块、可观察结果端；无新决策的内部结构明确预接，所有影响结果的线均可见。计算模块只有确有本关用途时才出现，不为“像 CPU”堆零件。

**玩家决定：** 来源与选择信号如何参与数据通路，而不是按颜色唯一配对。通过多个输入与选择值验证关系；不能只接受作者指定的那几条边或坐标。

**支架：** 点击输入可改变数值；就地显示方向和位宽；一个行为例子解释 MUX，但不显示整题接线。撤销与删除按需要教一次，不要求为了教学把正确电路拆掉。

**完成证据：** 可见方案通过完整行为用例。进阶调试可定位首个失败输入。结果出现后继续按钮就地可见。

### P-2 把结果留住

**任务：** 让机器保存当前结果，处理下一个值后，再把之前保存的值取回来。

**阶段：** A：寄存器写入/保持；B：两个地址分别保存；C：执行短 LOAD/STORE 序列并读回。每阶段只增加一个主要关系，上一阶段已验证的部分保留。

**玩家决定：** 何时写、何时保持、哪个位置被选中、读回值从哪里进入结果。控制器译码、无关常量等可以是具名标准模块，不要求同时重建整个 CPU。

**支架：** 行为表、操作含义、端口说明直接可查。常驻“当前输入／已保存值”；明确一次单步何时提交状态，不能混淆实时预览与已保存状态。

**完成证据：** 多组短序列都保持地址独立和读写正确。正式检查以行为为准，不能因绕开标准中间结构而拒绝正确方案。

**转场：** 机器已经会工作。接下来使用功能相同但专门计量耗时的系统模型，检查它为什么在等。不要声称四位门电路直接变成了物理八位处理器。

### 1-1 换了 CPU，为什么还慢

**任务：** 同一批工作换上更快的 CPU，看看总耗时改善了多少。

**固定：** 程序、数据、RAM、总线；只开放 CPU 替换，范围在任务中明示。此前已学的固定系统连接可自动保留，不再次要求配对接线。

**玩家操作：** 查看原方案并运行替换后的方案。可以自愿记下预期，但不要求先答题。程序在本关固定时应直接呈现只读任务程序，不提供一个能编辑却无法合理通关的陷阱入口。

**反馈：** 基线→当前的总周期和计算/等待变化；点击等待段定位相关请求。改进幅度由真实引擎返回，不在 UI 中硬写一个百分比。

**完成证据：** 当前工作结果正确，已有同条件的有效比较。该关允许较强引导，因为它负责建立反直觉；不要为增加“难度”逼玩家选一句已被图表直接说明的答案。

### 1-2 钱该花在哪里

**任务：** 机器还有一个升级机会。选对零件，让当前工作更快完成。

**场景：** 在同一任务内使用两个短配置：一个突出 RAM 服务，一个突出窄总线传输。两者必须由现有参数和引擎实际产生，不靠提示文字声称瓶颈不同。

**玩家决定：** 比较 CPU、RAM、Bus 的实际收益，选择允许范围内的改动。必要时以“一次只能替换一件”为公开任务约束；硬件成本可见，低预算作为额外目标。

**反馈：** 分段传输与 RAM 服务时间分开展示；不能把“走得远”解释成图上几何距离。完成后保留试其他方案的入口。

**完成证据：** 输出正确，满足实测可达的时间/改动约束。至少检查错误升级并非同样达标，以及换一种机器条件后最有用的改动确实可能不同。

### 2-1 别再跑远路

**任务：** 重复取数耗时很长。让机器利用一块小型快速存储，减少访问内存。

**玩家操作：** 从原方案启用缓存，查看第一次获取数据与后续命中的区别。固定程序与容量，先不增加策略选择的复杂度。

**支架：** 把实际取回的一块数据展示出来。解释这里的“近”指存储层级与访问成本，不是可随意拖动优化的距离；缓存内容由模拟器管理。

**完成证据：** 正确输出，实际发生首次远取和后续近返，并形成同任务前后对照。不要求把自动完成的机制再写成问答。

**记录：** 体验之后总结“缓存、命中、未命中”，但元件必要行为从一开始就能查到。不要把新人必需的规格锁为 `???`。

### 2-2 换个读取顺序

**任务：** 同样装着缓存，这批工作却频繁重取。保持硬件不变，修改程序的读取顺序。

**玩家决定：** 如何安排循环或受限程序，使取回的数据在被替换之前得到使用。任务正文不得直接说“交换两层循环”或“选行优先”。

**同屏证据：** 小型二维数据表、线性内存地址、当前缓存行、下一段实际访问序列和可编辑程序。地址预览必须来自解析后的 IR，不是根据按钮名生成的装饰。

**帮助：** 行为规格解释当前内存布局和缓存行大小；Hint 1 指向复用时机，Hint 2 揭示关键地址关系，Hint 3 才给参考程序。前台不要同时显示“使用最优行优先方案”的一键答案。

**完成证据：** 多个数值用例输出正确，在固定硬件下达到经引擎校准的目标。不要依靠程序文本签名或必须出现 `row-first` 标签判定所有合理实现。

### 2-3 这一小块，先做完

**任务：** 数据需要处理两轮。即使每轮读取连续，第二轮仍重新取回很多数据；不升级硬件，减少这些重取。

**玩家决定：** 多大的数据组能留住，以及离开它以前完成哪些已允许的工作。首版可保留现有有限 Work Group 选项，但每个选项必须展示真实执行安排。

**同屏证据：** “整表第一轮→整表第二轮”与“组 1 的两轮→组 2 的两轮”的序列；当前组、轮次、缓存驻留、远取与替换。

**正确性边界：** 两轮处理的输出契约、允许重排的条件必须写清；沿用现有工作负载语义。不能随意把两个有跨组依赖的 pass 交换，也不能不加说明就把现有每轮输出改成两轮求和。

**完成证据：** 工作量与每轮结果不变，减少重复获取并达到目标。自动测试检查实际访问计划，防止只改标签。无需在本轮实现通用分块编程语言。

### 2-4 最后一单

**任务：** 用已经学过的手段完成一项有约束的数据处理工作，并尝试更好的方案。

**新意：** 来自不同容量、轮次、部件条件或预算，而不是仅把输入数值换一遍。初版优先使用现有模型能表达的组合；不能伪装成已实现的大矩阵、冲突缓存或并行任务。

**自由度：** 开放已经学过的访问顺序、缓存容量、工作分组。Profiler 和规格可查，不强制先答诊断题，不锁住第一步只能改一个维度。比较视图如实提示此次改变了哪些项目。

**目标：** 基础通关为正确性＋合理耗时；“同样快但更便宜”作为独立额外目标。不把速度、价格和布局合成不透明总分。

**完成证据：** 至少两种实测有效方案，保留其中低成本软件方案。数值以引擎为准；完成后显示初始→最佳及不同方案的差别，并允许继续玩。

## 5. 难度与自由度规范

### 5.1 规格、提示、答案三分离

| 信息 | 默认访问规则 | 例子 |
|---|---|---|
| 规格 | 当下需要时随时可查 | 端口位宽、OP 表、状态提交时机、数组布局、测试目标 |
| 提示 | 按需、逐级提供推理增量 | 哪个事件值得追踪、哪两个地址值得比较 |
| 答案 | 明确选择后才展示 | 完整参考电路或程序 |

“体验先于术语”不等于“隐瞒操作规则”。玩家可以不知道怎么解，不能不知道判定规则和元件行为。

### 5.2 主线的两类玩家

新人获得清楚任务、行为例子、必要规格和可回看的提示；已有基础玩家可以略过说明并直接操作。使用同一套规则和验证，不制作两套维护成本高的主线。

公共操作只在需要时教一次。教学显示状态只是偏好，不是理解证明，不能因为点过手册就永久禁用帮助。可选工坊和优化目标提供深度，不靠增加必读页数区分高手。

### 5.3 接线自由与正确性

端口兼容只基于方向、位宽和电气约束。不得只允许作者希望的配对；相同位宽的“DATA 接控制端”是否错误应由功能测试解释，不能靠设计意图静默禁止。

预接线必须可见并明确属于初始机器；不能在玩家错误时用后台参考拓扑补齐。阶段验证依据可见行为，最终验证仍检查完整任务。

### 5.4 结果、工作量和性能不得混淆

输出正确不代表完成了规定工作；减少工作或删掉一轮不能伪装成优化。可比较运行必须绑定同一个任务版本、测试数据、初始存储状态、工作量和数值语义。

实验允许错、允许变慢、允许多项同时改动。多项修改时只能报告相关变化，不能把改进归因到某个未经隔离的单一因素。

## 6. UI / UX 信息架构

### 6.1 默认工作区

保留电路工作台和技术感，不再让第一次游戏变成窗口管理。默认稳定分区；不重新实现一个通用桌面系统。

```text
顶部：任务名｜简短目标与约束｜方案｜运行｜撤销｜帮助

中央主区：机器／电路／程序与数据关系
右侧上下文：任务规格，或当前选中元件的行为与端口

底部摘要：结果正确性｜总周期｜等待｜相对基线变化
底部展开区：回放与关键事件／失败用例／耗时明细／方案对照
```

首版可把中央工作区约 2/3 可用宽度作为布局起点，而非硬编码像素约束。程序和地址变化必须同屏的关卡，使用固定分割布局；不能把必须比较的信息藏到互斥标签。

### 6.2 七类工具的地位

| 工具 | 默认状态 | 主要职责 |
|---|---|---|
| Mission | 短目标常驻，正文可展开 | 当前任务、限制、可回看规格 |
| Components / Parts | 放置或更换时打开 | 本关合法供给、真实预览、简短用途 |
| Inspector | 选择对象时替换上下文详情 | 功能、端口、位宽、当前状态；必要时钉住一张比较卡 |
| Test Bench | 运行入口常驻，输入/用例按需展开 | 当前输入调试与完整任务验证 |
| Trace | 时间轴和关键事件入口 | 图、代码、地址、状态之间的同步定位 |
| Profiler | 结果摘要常驻，明细可展开 | 耗时分解；点击定位原事件，不指定答案 |
| Handbook | 一个统一入口 | 合并术语手册与 Notebook；经历记录附在条目后 |

Run History 并入“方案对照”，默认基线、当前、个人最佳，不另开常驻浮窗。必须同时查看的信息可钉住或并排；完整浮动/分离不作为本轮交付前提。

### 6.3 视觉焦点与信号语言

| 状态 | 第一视觉焦点 |
|---|---|
| 刚进入 | 目标和本阶段要处理的对象 |
| 正在编辑 | 当前对象、合法连接反馈、局部状态 |
| 查看执行 | 当前等待或处理事件，以及它关联的数据 |
| 运行失败 | 首个有解释力的反例及期望/实际 |
| 优化成功 | 减少的等待/远取和明确的继续入口 |

电平采用数值＋形态的冗余编码。低电平是正常值，不使用与失败相同的危险语义；输入/输出方向恒定，不随 0/1 变化。现有线色选择保留为用户标记，电平、活动、选中、错误使用互不混淆的视觉层。

位宽就地显示，例如 `DATA[4]`、`OP[2]`、`ADDR[1]`。交叉不自动连接，分支必须显式。寄存器值、RAM 地址与内容、缓存行驻留持续可见，而不是只有播放瞬间看得到。

不以移近元件、缩短线长、增加线段动画模拟更低延迟；普通连线和几何位置不产生性能成本。

### 6.4 操作与可访问性验收

单击主体选中、拖动主体移动、端口接线，优先级稳定。放置预览与落点一致；擦除范围和实际接触一致；从已有线网分支自然；所有拒绝都解释原因。保留撤销/重做。

回放和 Hint 可 pan、zoom、inspect，不锁住观察。Esc 先取消当前手势或关闭最上层，再逐级返回；一次按键不跳两级。

文本不能靠颜色识别，默认字号可读，提供合理 UI 缩放。首轮检查 1280×720、1600×900、1920×1080 及窗口/全屏切换；这是新增 QA 目标，不是现状支持承诺。低分辨率以折叠次要内容换空间，不把图表与端口缩成不可读。

### 6.5 运行与回放分离

“运行当前方案”在程序合法时建立不可变执行快照，再产生权威结果。输入无效就指出位置，不能偷偷运行旧程序而展示新草稿。

有状态调试保留“推进一步／复位状态”，必要时与“完整验证”区分；不必强行把所有语义合为一个按钮。新设置只影响新运行，旧结果明确显示其所属方案。

默认回放速度用 `1× / 2× / 4×` 等表达；原先要求的 Hz 可保留在高级显示中。两者都只改变观察节奏，不改变仿真。

完整验证计算结束即记录通过，显示非遮挡成功条；不必等动画结束。允许暂停、跳关键事件、直接查看结果。播放后续旧结果时不能覆盖新运行的显示。

## 7. 玩家文字与轻情境

### 7.1 统一三种声音

**任务：** 要完成什么，限制是什么。\
**规格：** 元件怎样工作，输入输出和状态有什么规则。\
**反馈：** 发生了什么，下次可检查哪里。

初始任务正文通常约 60–100 个汉字；复杂规格使用表格、局部例子，不为字数删除规则。已学操作不重复讲。轻情境限一两句，不新增对话树、大量角色和过场。

可采用“预算有限的设备维护站”作为暂定语境：接通旧机器、处理记录、工作增加、升级受限。此为可替换包装，不得影响仿真规则，也不能在没有队列模型时宣称实现了真实排队积压。

### 7.2 文案词典

| 对象 | 中文模式默认 | 技术标识 |
|---|---|---|
| Workbench | 方案／工作区，按实际对象区分 | 方案 ID 内部保持稳定 |
| Mission | 任务 | 不把内部 level type 暴露给玩家 |
| Trace | 执行记录／回放，按上下文区分 | Trace 用于开发文档 |
| Profiler | 耗时分析 | 首次说明可附英文 |
| Baseline / Current / Best | 初始方案／当前方案／个人最佳 | 内部保留原字段 |
| Cache / line / pass | 缓存／缓存行／轮次 | 代码中的名称不翻译 |
| Official Test | 完整验证／本关测试 | 调试与验证语义仍区分 |
| Controller / Register / MUX | 控制器／寄存器／数据选择器 | 画布、规格、手册使用同一名称映射 |
| OP / ACC / LOAD_MEM | 保留原标识并提供解释 | 不擅自改程序语法 |

项目显示名称统一使用一套写法；仓库名、资源路径和稳定 ID 不因中文润色改名。

### 7.3 改写标准与例子

| 不宜作为常态玩家文字 | 新表达 |
|---|---|
| 抽象层已建立 | 全加器做好了。 |
| 测试证据、拓扑签名与行为契约已绑定 | 已保存为全加器，后面可以直接使用。 |
| 提交 baseline 诊断后解锁完整 breakdown | 删除这项流程；入口为“查看耗时明细” |
| Trace 播放完成；结果早已由模拟器确定 | 回放结束。 |
| 官方 workload / deterministic Trace | 本关任务／执行记录 |
| 不知道哪里有问题的“正式测试失败” | 第 3 个用例未通过：应为 7，实际为 3。 |
| 含糊的“无法连接” | 位宽不匹配：4 位输出不能接到 1 位输入。 |
| 每次成功宣称“你已经理解……” | 这次少取了 4 个数据块，总时间缩短了 72 周期。 |

最后一行是句式示例，数值必须由对应运行生成，不能硬编码用于所有关卡。来源签名、确定性和精确拓扑仍可存在于开发诊断页，不要在普通任务中反复强调。

### 7.4 一组任务与提示范例

**任务：换个读取顺序**

> 缓存已经装上，处理这批数据却更慢了。\
> 修改读取顺序，让结果保持不变，并在规定周期内完成。不能更换缓存。

**Hint 1：** 下一次读取的数据，还在刚取回的那一行里吗？\
**Hint 2：** 一次会取回连续四个数。检查程序是否先使用了这四个数，再跳到另一行。\
**Hint 3：** 显示参考程序，明确标注它是答案；不能替换玩家方案或自动完成关卡。

读者不必看到其他报告就知道文案目标。文案实施必须查调用点，区分现行显示、历史备用和死字符串；同步中英文目录、占位符与术语，不只修改截图里的一句话。

## 8. 技术架构：保留计算内核，重构外层体验

### 8.1 推荐的职责分层

```text
内容定义：主线/工坊、目标、供给、测试集合、提示、文案键
    ↓
玩家方案：电路 / 已应用程序 / 部件配置 / 分组选择
    ↓
既有领域仿真：Circuit/Prologue ｜ System ｜ Locality
    ↓
权威运行结果：事件、输出、状态、指标、不可变运行记录
    ├─→ 关卡目标评价与可恢复完成状态
    ├─→ 统一展示适配：工作区、回放、耗时、比较
    └─→ telemetry 观察记录（不得反向决定结果）
```

这是职责图，不要求 Codex 建立同名新文件或一套通用插件框架。先复用现有类和 Godot 控件；只有两处真实重复且语义一致时才提取共享组件。

### 8.2 必须保持的不变量

1. 仿真确定性、独立于 UI。事件和结果是权威；动画不得计算另一套结果。
2. 显示的电路和已执行程序真实决定行为。不得用参考电路、隐藏程序、任务名分支替代玩家方案。
3. 普通导线、接点和几何距离不计延迟；RAM、Bus、Cache 等模型部件拥有相应成本。
4. 缓存由硬件模型管理；不新增手动装填玩法替代命中/替换机制。
5. 不静默截断或拓展位宽，不静默运行旧草稿，不虚构兼容的来源签名。
6. Game/Test 严格隔离；测试辅助不能写入正式成就、组件库或持久化进度。
7. 新旧运行证据不能混用。目标只读取与当次任务和方案匹配的结果。
8. 本轮保持仓库规定的 Godot 版本及强类型约定，不顺手升级引擎或引入重型依赖。

这些约束继承现有工程边界；以下分层改造是实施建议。[R1][R2]

### 8.3 需要修改的边界

| 领域 | 复用基础 | 本轮修改 |
|---|---|---|
| 内容与入口 | `src/content/`、章节目录、hub | 主线/工坊分类、8 节点依赖、正式入口与继续 |
| 基础任务 | `src/circuit/`、`src/hardware_foundations/` | 标准模块的合法供给、可见预接、行为阶段、编辑器回归 |
| 系统性能 | `src/system_lab/` | 两个任务和多配置比较，减少预测/诊断锁 |
| 缓存与程序 | `src/simulation/`、`src/locality_chapter/` | 合并任务、透明分组、多用例、按行为/性能判断 |
| 工作区 | `src/ui/` 及各章视图 | 固定主布局、上下文详情、运行摘要和统一比较 |
| 手册与文字 | `src/ui/terminology_handbook.gd`、`localization/*.po` | 统一入口、规格可查、运行文案审查 |
| 存档与组件 | `src/save/`、PlayerContentState、workbench | 独立进度映射、标准/自建来源、保护旧设计 |
| 数据观察 | `src/playtest/` | 版本与语义动作分类，问卷频率降低 |

路径是依据版本中已有的边界，实际实现前查最新调用点。[R1] **不要为了表格整齐把三个 simulator 合并。** 薄的展示适配可以统一字段标签，但缺失指标标为“不适用”，不能为统一界面计算假指标。

### 8.4 三种状态必须独立

- **方案状态：** 电路、草稿、已应用程序、当前部件和工作分组。
- **运行状态：** 对一个冻结方案和测试集合产生的结果。
- **展示状态：** 选中对象、缩放、窗口、回放位置、提示页。

展示变化不应让运行证据失效；影响行为的方案变化应明确使“当前结果”过期。保留旧运行作为对照，而不是删掉它后又让玩家重复建立基线。

“已通过关卡”与“当前草稿是否通过”分开：修改一个通关后的草稿可以使当前方案待验证，但不能无提示抹去所有历史成就。

### 8.5 标准组件与自建组件

标准组件是新的正常 Game 内容供给，不是临时测试作弊组件。它们有明确稳定标识、行为版本和验证用例，界面标注“标准组件”。

工坊成果保留原电路快照、命名接口和来源，界面标注“由你构建”。同一行为若允许互换，必须验证接口与输出契约；不能因名字相同就认为兼容。

主线可以使用标准组件，不要求伪造已完成 Half Adder、ALU 或 TinyComputer。用户在工坊修改组件也不能把主线重新锁死。初版无需强行支持任意工坊模块替换主线性能模块。

### 8.6 三层模型的玩家说明

序章采用小位宽构建与状态模型，第一章是 CPU/RAM/Bus 的系统耗时模型，第二章是数组与缓存模型；它们不是完全相同的一台物理机器。[R1][R4][R5]

过渡处用一句话说明变化，手册给出完整边界：普通线不计延迟、模拟周期不是回放速度、图上距离不决定速度、不包含完整取指/流水线/并行与真实物理时序。

CPU 等待通常已经包括内存与总线的等待，不能把它和 RAM/Bus 再作为互斥时间块相加。“占比过半”只是现行分类办法，不能教成瓶颈的普遍定义。分块合法性取决于当前任务依赖，不能宣传任意程序都能重排。

## 9. 关卡评价、基线与性能校准

### 9.1 新的完成依据

完成状态应主要由“输出正确＋工作量符合契约＋公开约束满足”决定。个别入门对照任务可要求产生一对有效运行，但不能常态要求先作答、先看动画或必须打开某个工具。

等价正确电路与合理程序允许通过。不要用参考边列表、固定组件 ID、字符串完全匹配代替行为验证。需要锁定硬件或工作负载的关卡直接说明并约束可操作范围。

### 9.2 保留真实基线，不制造重复劳动

合并关卡直接保留上一阶段基线。必要时可用引擎计算作者初始方案，标明“初始方案参考运行”，不伪装成玩家亲自操作。玩家仍能重放和自行复测。

比较所用数据、任务版本和初始缓存/内存状态必须一致。默认每次完整验证从规定初态开始；不能某次热缓存、某次冷缓存却不说明。改变问题本身时，要建立新对照组。

### 9.3 参考数值的使用边界

下表来自旧版参考工作负载，不是新版任意数据、任务和配置的保证。[A1][R5]

| 旧参考方案 | 总周期 | RAM 字节 | 硬件成本 |
|---|---:|---:|---:|
| 单轮、直接 RAM | 257 | 64 | 0 |
| 单轮、一行缓存、列优先 | 321 | 256 | 4 |
| 单轮、一行缓存、行优先 | 105 | 64 | 4 |
| 两轮、一行缓存、整表行优先 | 210 | 128 | 4 |
| 两轮、一行缓存、按一行分组 | 138 | 64 | 4 |
| 两轮、四行缓存、不分组、列优先 | 138 | 64 | 13 |

实施前用当前引擎重算并保留回归。新关卡先生成允许方案的结果表，再确定门槛；不要先写“105／145 周期”，再偷偷调仿真让它通过。

多输入数值用例检查正确性；新访问结构或不同约束检查迁移。两者不能互相替代。固定结果为 88 的参考，不足以证明程序处理所有合法数据正确；也不能据此未经验证就宣布存在绕过漏洞。

### 9.4 方案空间检查

每个性能任务至少检查：初始方案、预期成功方案、看似合理但无效的修改，以及所有实际可枚举的离散硬件/分组组合。终关检查至少两个有效方案及低成本方向。

程序空间未完整枚举时，报告“当前测试覆盖的有效方案”，不能宣称全局最优或穷尽。无法在现有机制内形成有意义选择时，先调整任务，不先增加新模拟器。

## 10. 存档、迁移与旧成果保护

这一节是本轮必须新增的兼容性设计，不是现有存档已支持的功能。

**默认不删除、不覆盖旧方案、不自动重置进度。** 开始前检查工作树并备份实际格式；最终用户仍是提交和集成者。未明确授权，不 commit、push、merge 或执行破坏性清理。

建议新主线用与旧工坊不同的稳定 ID；显示标题可以改变，ID 不因润色改变。内容版本、保存版本和仿真行为版本各有边界，不因颜色或布局更新使功能来源失效。

旧完成记录按证据保守映射：相同契约且可重新验证的内容可以迁移；只知道“旧 ALU 已完成”不能等同于“新主线全部通过”。无法映射的记录作为旧工坊历史保留，不伪造验证结果。

已封装组件保持独立快照；编辑者另存新版本，不静默修改其他方案引用的版本。现行依赖校验保持有效，但不要用关闭校验解决误清进度。

新版至少保存当前关卡/阶段、当前方案、有效的标准/自建组件来源和完成记录。对性能关保存程序与配置以及必要的对照身份；完整 Trace 可恢复时重算，不必把所有瞬时动画状态写入存档。恢复后明确标记重算结果与未运行草稿。

必须测试：迁移前后旧命名方案不变、重启能继续、缺失组件来源不被伪造、损坏/未来格式安全失败、部分写入可恢复、Test 结果不进入 Game、尝试新设计不无警告摧毁历史完成。

## 11. Codex 实施路线：先闭环，再铺开

### 11.1 本轮执行授权与边界

完整目标是八关主线和工坊重新定位，不是只做两关后宣布全部完成。实施必须按可运行里程碑推进，不做一次性全仓库替换。

先按 `PLANS.md` 建立一个简要执行计划并立即实施。[R3] 无需用户重复批准本文已决定的路线。没有真人试玩结果时可以继续已确定的工程工作，但不能声称已验证有趣，也不要在核心短切片尚不可运行时扩张全局架构。

### 11.2 分阶段交付

| 阶段 | 工作范围 | 工程完成证据 | 人工验证状态 |
|---|---|---|---|
| M0 基线与旧约束核对 | 读实际 HEAD、AGENTS、PLANS、架构、旧修复计划和相关测试；分类旧问题；建立保护方案 | 版本、受影响文件、原始测试结果、替代旧决定清单 | 不要求先取得新的完整试玩 |
| M1 核心短切片 | 做“CPU 更快但仍在等”和“缓存无效→改访问顺序”；接入最小新工作区、对照和必要短文案 | 两段可真实操作；引擎结果正确；普通模式语义合法；无答案注入 | 新人理解和趣味待实测，不可由 AI 自评替代 |
| M2 主线与工作区 | 八节点主线/工坊入口、合法标准组件、存档迁移；推广 M1 的共享展示 | 正常 Game 路线无工坊前置，旧方案可继续；基础运行入口稳定 | 检查是否仍先忙于排窗 |
| M3 关卡完成 | P-1/P-2、RAM/Bus 场景、缓存/分块、终关多解；引擎校准阈值 | 行为验证、公开约束、多解及反例测试；无无意义流程锁 | 新人可解性与节奏待试玩 |
| M4 统一体验 | 全玩家路径文案、手册、信号状态、快捷操作、分辨率、低打扰反馈 | 可达文案审查；窗口/全屏、缩放和输入回归；不遗漏旧场景 | 熟手无重复教程负担 |
| M5 集成与交付 | 全量回归、普通 Game 冒烟、导出试玩构建、文档更新 | 构建与运行日志、截图/操作验证、diff、已完成/未完成报告 | 新人/熟手试玩结果单独登记 |

M1 是开发用短切片，可通过明确的内部试玩入口进入；它不能靠开启 Test 模式来掩盖正常流程错误，也不能成为正式玩家永远绕过基础的意外入口。M2 完成后临时入口移除或限定为开发使用。

M4 的“全量统一”不是前面可以使用乱码、开发键和占位段落的理由。每个里程碑从第一次可玩起就使用合适的文案和基本布局。

### 11.3 第一轮对 Codex 的最低交付要求

**至少完成 M0＋M1 的可运行闭环，而不是只写计划。** 若当前执行条件允许，继续推进后续里程碑；不能为宣称全量完成而提交八个空壳或让多个系统处于半迁移状态。

任务被执行边界中断时，把当前状态、验证结果、下一条可执行步骤写回计划，保留可运行项目。单独列出剩余项，不能把“有接口／有字符串／测试全绿”写成“玩法已经成立”。

### 11.4 测试如何随重构更新

旧测试分为三类：保留的不变量、需改写的产品行为、真正废弃的旧断言。对诊断锁、强制地图数量、完成必须等待动画等断言，注明由哪项新设计取代，并新增反向回归。

禁止仅删除失败断言来制造绿灯；禁止为了通过旧测试重新加回旧产品门槛。仿真、来源、存档、输入边界仍要有独立覆盖。

可以用子任务并行审查文案、测试或只读定位，但共享场景、存档格式和核心控制器应由同一条集成线负责，避免多代理互相覆盖。不要求建设复杂 agent 调度系统。

### 11.5 必须交付的简短报告

报告包含：实际改动；可运行入口；测试命令与结果；正常 Game 流程验证；截图或输入回归证据；语义/存档变化；仍待人工试玩的项目；剩余里程碑。没有运行某项就明确写未验证。

## 12. 验收：工程与体验分别判定

### 12.1 工程验收

| 范围 | 关键要求 |
|---|---|
| 仿真 | 同一输入与方案结果一致；回放速度、语言、布局不改变结果 |
| 内容 | 主线 8 节点可依次推进，工坊不是必需依赖；对照任务没有重复基线负担 |
| 权威 | 可见电路和实际程序驱动结果；参考答案不进入玩家证据；相同功能不同结构可通过 |
| UI | 运行、目标、失败点易定位；pan/zoom 后点击和落点正确；信号/选中/错误可区分 |
| 完成 | 无强制答题与观看锁；成功不挡工作区；继续优化不会丢失历史完成 |
| 程序 | 无效草稿不会被当作已执行；运行快照和结果一致；工作量不能被删减绕过 |
| 状态 | 初态、单步提交、预览、保存值清楚；新旧 Trace 不相互覆盖 |
| 保存 | 旧命名方案保留，版本迁移可恢复，Game/Test 隔离，无伪造来源 |
| 文案 | 玩家可达键无占位符、混用和失真；技术行为与说明一致 |

使用仓库实际测试指令，不猜不存在的命令。没有 Godot 或图形环境时，记录限制；headless 测试不能冒充鼠标实际可用或视觉清晰。

### 12.2 真人试玩

完整版首轮建议约 6–8 位目标新人及 3–4 位已有基础玩家。[A1] M1 可以先由更少人数进行定性排障，不必为凑人数推迟第一个观察机会。任何这类小样本都不能当市场统计。

使用隔离、干净的普通 Game 存档。不要把 `--test-mode` 的直达关卡、临时组件和解除限制当作正常通关。当前内部试玩说明存在使用测试模式的示例，实施时应单独补充正常路径验收方法。[R5][R7]

开发者不主动补规格。需要救场时先记录阻塞位置与玩家理解，再干预；干预后的通过不算独立完成。

重点问：目标是否清楚、为什么改这里、哪种事件减少了、换一个条件是否还成立、是否愿意继续优化。不要用强制知识问卷取代自然操作观察。

### 12.3 首轮体验门槛

- 大多数目标新人不看完整答案，也能走通基础任务和首次性能改进；报告实际人数、干预和 Hint 使用，不捏造总体成功率。
- 熟手能跳过已知说明，不反复证明会接线或会点击运行。
- 同一位置连续出现两名玩家“完全不知道下一步”，列为高优先级设计问题；不能用平均满意度抵消。
- ALU 一类“顺利但无聊”的反馈单独处理，不能靠降低失败率宣布解决。
- 回放、说明与窗口操作没有取代主要思考；完整时长和主题到达时间按实测调整。

这些是本项目验收建议，不是已由外部作品验证的硬性阈值。

## 13. Telemetry：记录决策，不增加考试

保留现有匿名本地记录和可跳过反馈，保持观察者定位。[R7] 不增加账号、远程分析后台或实时 AI 导师。

优先补充：构建/关卡版本、Game/Test、首次有效运行、首次性能改进、Hint 级别、连接拒绝原因、程序/硬件/分组的语义修改、纯布局修改、主动重放关键事件、通关后优化。

区分自动打开的工具与玩家主动打开；不要把工具曝光次数当作理解。用时如无法可靠区分思考、离开和查阅，就按原始时长报告，不伪称“有效思考时间”。

每个微阶段不弹问卷。短反馈放在关键节点或关卡结束，长反馈在章末；所有反馈可跳过。不要为了测“预测准确率”重新给正常玩家加预测锁。

## 14. 优先级与不做清单

| 优先级 | 本轮内容 |
|---|---|
| P0 | 可运行核心闭环、真实输入 Bug、缺失规格、正常 Game 可推进、数据安全和结果可信 |
| P1 | 完整八关路线、稳定工作区、关卡决策与多解、统一文案、即时反馈和可比较结果 |
| P2 | 已有工坊的进一步节奏优化、克制音效、进阶布局偏好与非必要视觉细节 |
| 暂缓 | 新章、流水线、预取、多核、真实物理时序、通用 HDL、任意位宽、可编辑 ISA、大规模叙事、联网排行榜和素材管线 |

也不做：为了少写关卡而加入实时 LLM 出题/讲解；为了统一类名重写全部 simulation；为了凑时长把合并的观察节点再拆回去；为了形式自由提供大量无法影响结果的开关。

遇到同样的卡点，优先检查“规格是否可见、操作是否可靠、决策是否明确”。最后才考虑增加一段文字。

## 最终实施准绳

> **最应保留的是可信的因果，最应重做的是玩家到达因果的路径。**
>
> 玩家不必先重建整门计算机课程，才获准体验数据移动的代价。让他尽早看到问题、拥有足够规则、作出真正改动，再从机器的行为中得到回应。
