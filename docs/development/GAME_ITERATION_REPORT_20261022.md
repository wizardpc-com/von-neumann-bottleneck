# 《冯·诺依曼瓶颈》迭代与试玩报告

> 更新截至 2026 年 10 月 22 日 10:52，北京时间。工作范围：在既有实验室与全屏终端版本上优化，不另起一套游戏，不改变仿真规则。以下明确区分已实现、已验证与尚未验收的内容。

## 一、先说结论

本轮重点不是继续堆功能，而是把「第一次接线 → 构建 → 正式测试 → 封装 → 下一关复用」这条体验链做得更清楚，并改善元件表现和关卡关系。

代码基于 `a5965e3725638cb87e93ffb0a05b95abe12c4dba`，在 `codex/component-visual-v2-20261022` 分支开发。上午延长轮的功能提交为 `f40bf89`。**目前仍是候选版本，不等同于已经可以直接参赛的最终作品。**

## 二、主要完成了什么

### 1. 新手操作引导

- 增加只读虚拟鼠标演示，指向真实端口和按钮，可重播、停止，并响应减少动效设置。
- 演示不替玩家接线，不改输入，不奖励完成；玩家开始操作时，演示立即让位。
- 第一关集中练习接线、改变输入、运行、拆线、重接。较长的编辑/撤销说明放到全加器，缩放/平移说明放到寄存器，避免一开始塞满教程。
- 序章各关有不同的短操作重点。构建提示现在先提醒使用画布已有元件，再按需要拖入新元件，避免误导玩家必须重新放置整套零件。
- 修复正式测试已经全通过，教练仍要求重复调试的问题。
- 上午实际试玩进一步发现并修复：后续序章按 F6 会运行电路，但教练未同步推进；现在快捷键和按钮共用同一入口。
- 关闭元件/测试台面板，或者搜索导致元件列表为空后，点击演示不再无响应，会说明恢复方法。尊重玩家选择，不擅自重新打开面板。

**边界：**尚未给每一种后期操作都制作独立动画。当前是关键手势演示加分散的文字教学，不是全流程自动带玩。

### 2. 元件体系与玩家自己的封装外形

- 封装成功时，从玩家当前实际布局提取并冻结独立视觉记录；之后仅移动工作台上的零件，不会篡改此前封装外形。
- 画布元件、元件栏缩略图和轮廓预览共用几何规则，减少同一个元件在不同位置表现不一致的问题。
- 保留稳定接口、位宽和端口顺序，统一低饱和家族颜色，并区分选中、悬停和运行状态。
- 视觉记录独立于逻辑签名与仿真。旧存档、未知版本或损坏的视觉字段安全回退，不凭空恢复历史布局。
- 修复轮廓分段处引脚连接不一致的问题，补充大量布局与几何边界测试。

**边界：**现有游戏每个命名成果仍只有一个活动定义，例如 HalfAdder；没有悄悄改造成可以同时保存任意多个历史版本的元件工厂。整体美术风格也还需要你最终审阅。

### 3. 关卡树和关卡之间的关系

- 区分真正的前置条件、后续任务与推荐路线，避免把建议路线看成硬性门槛。
- 调整跨章节连线，改进实线/虚线、箭头和选中关系的辨识度。
- 全图能容纳 60 项任务与 11 个章节区域；缩放和窗口变化尽量保持视野连续。
- 修复英文长标题把详情阅读区挤到只剩几像素的问题，保留固定的进入按钮和状态，长内容在正文内滚动。
- 缓存连线几何，减少平移和悬停时的重复构造。这个优化有代码与回归依据，但不能直接换算成某个 FPS 提升。

### 4. 作品与方案的真实性

- 作品预览使用实际保存内容，不用示意图冒充玩家作品。
- 新方案明确说明从初始元件开始，原方案仍保留，避免误以为这是复制当前方案。
- 补充保存、重启、反复进出终端和工具页的测试，维护原有反馈与存档保护边界。

## 三、实际怎么玩过

在 Ray 自己的 Linux 云电脑上，使用隔离试玩存档，进行了真实鼠标与键盘操作；不是给玩家档案注入完成记录。

1. 实验室进入终端、地图与首关；看到虚拟光标，完成五步接线练习。
2. 手动连接半加器，四组正式输入全部通过，点击封装。
3. 在下一关看到并复用刚才封装的半加器，搭出全加器，八组正式输入全部通过，再封装。
4. 重启后，3/60 进度和可复用元件正确恢复。
5. 在修复后的源码版本中，手动连接 SR 锁存器，验证 F6 教学推进和关闭面板恢复提示，正式状态序列通过并封装。
6. 再复用锁存器搭建一位寄存器，写入/保持序列通过并封装。
7. 重新导出后，用 Linux 引擎直接载入该包的内嵌游戏内容，5/60 进度恢复。手动连接一位 ALU，四组操作共 32 个正式用例通过并封装；随后连接 2×4 RAM，五步写入、覆盖与读取序列通过并封装。
8. 两条分支汇合后，手动搭建四位累加器 CPU。七步完整程序全部通过，最后 ACC=7、M0=3、M1=7，并封装 TinyComputer。正常退出再启动后，8/60 进度仍在，下一项正确指向 LOAD/STORE 桥接实验。还检查了英文终端、地图和 CPU 详情，前置、后续任务与固定进入按钮均可见。

这些分轮试玩覆盖了从接线到运算、存储，再汇合成 CPU 的八项核心构建任务；不是在同一次新安装运行中重玩全部八项，更**不是从头到尾通关全部 60 项任务，也不证明新玩家一定理解每一关。** 当前云端使用 Mesa llvmpipe 软件渲染，音频回退为空驱动，不能据此宣称已完成 Windows 显卡性能或音效验收。

### 真实渲染发现的性能缺口

在云电脑实际 1364×1024 分辨率、llvmpipe 软件渲染下，每种状态采样 180 帧：外部房间约 **2.8–2.9 FPS**，进入全屏终端后约 **60 FPS**，后者已暂停后台 3D 渲染。这意味着不能把当前版本称为在云电脑上整体丝滑。

我做了两组隔离对照：关闭动态阴影和抗锯齿后房间约 16 FPS；再把 3D 分辨率减半约 27–28 FPS，但墙面小字明显变糊。两者都没有达到 60 FPS，且后者损害美术与可读性，**没有把这些试验直接塞进交付版本**。正常硬件渲染画质未被悄悄降低；Windows 目标机器仍需独立验收。

## 五、接下来最值得做的事

### 第一优先：入口性能与陌生玩家的真实卡点

先在实际提交机器上验证实验室进入、离开终端和密集关卡的帧时间。如果低配设备仍卡顿，应做可选择的低负载房间或静态入口，保持文字可读和交互准确，不能只靠降低分辨率遮掩问题。

找没有计算机背景的人，从全新存档开始，先只观察到半加器与第一次封装复用。记录「下一步不知道点哪里」「知道怎么操作但不知道目标」「得到结果却不懂原因」分别出现在哪里。不要用更多文字掩盖交互问题，也不要把测试通过当作好玩。

这次试玩还看到一个具体卡点：CPU 关卡在云端窗口同时打开多个工具面板时，自动适配只有 53%，端口文字偏小；收起面板再按 Shift+Home 可以恢复到 100%。操作本身有效，但更好的默认布局和及时提醒，比再加一页长说明更有价值。

### 第二优先：逐关的思考节奏和反馈

把每关的关键发现压缩成一句话：玩家应该先猜什么，能亲手改变什么，运行后哪条证据说明对错，完成后新能力在哪里派上用场。优先处理序章两条分支汇入 CPU 的跨度，以及从构建转入性能分析时的目标变化，而不是平均给所有关卡加装饰。

### 第三优先：统一视觉并做目标机器验收

在实际提交使用的 Windows 机器上，检查小尺寸端口文字、长标题、密集电路、地图关系和全屏切换；记录帧时间与最低流畅度，而不仅是平均 FPS。再统一元件比例、留白、提示卡密度和过渡节奏。声音需要有真实输出的设备单独检查。

### 第四优先：叙事服务于解谜

让壹的回应对应玩家刚完成的发现，少重复操作说明；在章节转换时解释为什么现在需要下一种能力。保留「理解它，而非依赖它」的主线，但不要在玩家尚未理解规则时堆背景文字。尚未确认的故事设定不应直接当成定稿。
