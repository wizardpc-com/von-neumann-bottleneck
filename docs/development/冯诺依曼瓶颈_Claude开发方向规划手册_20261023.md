# 《冯·诺依曼瓶颈》Claude 开发方向规划手册

**本轮重点：美术与 UI、元件实际观感、关卡操作与探索体验。**

> 在现有版本上，把“已经做出来的功能”打磨成清楚、统一、有吸引力的游戏体验。本文确定需要解决的问题和期望效果；具体构图、布局、视觉方案、动效与实现方式，由 Claude 结合实际游戏自主设计。

- 壹的存在自然、有温度，但不会抢占画面或替玩家完成探索。

## 2. 工作重心与优先级

| 层级 | 本轮重点 |

| 优先消除 | 阻断操作、遮挡关键内容、端口与图形错位、状态错误、无法返回或保存等实际问题 |

## 3. 美术与画面：形成统一、克制但有辨识度的作品

### 3.1 整体视觉语言

延续已经确定的方向：**温润、明亮、简洁的未来实验室，与深色、清晰、安静的计算工作台。**

重点检查：

- 实验室、终端、关卡、档案、作品展示是否属于同一套设计语言。
- 背景、面板、正文、元件、线路和状态强调是否有明确主次。
- 边框、圆角、阴影、字号、间距和图标是否一致，是否存在局部精致而整体拼接的感觉。
- 画面质感是否来自构图、比例和细节，而不是额外堆叠发光、渐变、装饰线和副标签。
- 暗色界面是否沉闷或辨识度不足，浅色页面是否有文字、图解和状态看不清的问题。

可以调整已有配色与细节，但不要使装饰色与信号、错误、选中等状态含义混淆。

**完成效果：** 第一眼能找到当前操作对象；连续切换章节时，不感觉换了一款游戏。

### 3.2 元件与线路

新参考形状已经进入当前版本，本轮以它和用户最新认可的素材为基础做实际效果校准。[S3]

- 保持元件家族统一，同时让逻辑、选择控制、存储、运算和系统设备容易区分。
- 检查名称、功能符号、端口、位宽和当前值之间的主次，不让内部装饰挤占有效信息。
- 检查元件台、拖动预览、实际放置、封装和后续复用是否一致。
- 在简单电路与密集电路中都看效果；关注线多时的端口定位、交叉关系、选中状态和错误定位。
- 检查缩放、拖动、连接、拆线、运行与等待状态，避免静态图好看但操作时难用。
- 保留玩家自制模块的来源感与可辨识外形，不让所有封装成果都退化成同一个通用盒子。

**完成效果：** 元件既更精致，也更容易理解和操作；新风格不只在元件总览图里成立。

### 3.3 实验室与功能页面

- 以最新已确认的小型封闭实验室、中央深色一体化终端为基础，保持终端的视觉中心地位。
- 档案、旅程、作品和辅助装置各有功能含义，既能被找到，又不与主入口争夺注意力。
- 精修物件与页面之间的联系，使进入、退出、继续游戏和返回房间符合直觉。
- 检查空状态、已解锁状态和获得成果后的变化；不要为丰富环境增加没有用途的装置。
- 沿用现有场景与交互成果，不再把选择2D、伪3D或3D技术路线作为本轮任务。

**完成效果：** 实验室像一处真正用于学习和创造的空间，而不是漂亮背景上贴了一组按钮。

## 4. UI与交互：把屏幕空间还给操作

### 4.1 导航与信息密度

- 继续审视顶栏、工具栏、状态栏和重复标题的实际价值，减少长期占位却很少使用的内容。
- 保证运行、调试、查看结果、封装和保存等当前关键动作容易发现。
- 整理设置、模式、地图、手册等入口的层级，减少重复入口；简化不能变成把重要功能藏起来。
- 已有游戏／测试模式切换属于当前版本功能，优化布局时保留其可发现性与模式隔离。[S2]
- 用布局、对齐、分组与反馈解释界面，避免依赖越来越多说明标签。

### 4.2 窗口、卡片与阅读层

- 同一时刻只保留一个主要引导内容；任务、求助、完整说明、设置和结算不要互相争夺画面。
- 关闭、切换或离开页面后，旧提示、动画、焦点与点击区域都应结束或正确恢复。
- 拖线、输入和调整参数时，界面不要突然移动、展开或打断操作。
- 保留工具之间必要的并排比较，不必把所有窗口强行改成相同形式。
- 检查小窗口、全屏、常用缩放和较长文字下的可读性与可点击范围。

### 4.3 后期高密度工作台

表示、服务、预测、压缩与创造等区域仍应列为重点检查对象。已有引导收敛交接明确记录过这些区域尚未完全统一，执行时先核对最新实现再修改。[S5]

- 让玩家能区分正在编辑的方案、已运行的记录、当前结果和历史作品。
- 让主要操作和主要结果相互关联，不要求在多个区域来回寻找。
- 次要参数、详细事件和高级证据可以分层呈现，但当前任务所需信息必须可用。
- 统一返回、求助、运行、比较和保存的交互语言，同时保留各类玩法的差异。

**完成效果：** 减少寻找按钮和管理窗口的负担，而不是仅仅减少屏幕上的文字数量。

## 5. 关卡体验：不仅能通过，还要有实际发现

这一部分与美术、UI同等重要。不要只优化首页，也不要将关卡改进等同于改写任务说明。

### 5.1 检查每关的玩家过程

对准备修改的关卡，先弄清四件事：

1. 玩家本关要解决什么具体问题，能改变什么。
2. 玩家第一次进入时，是否知道如何开始。
3. 失败或成功时，是否能理解自己的操作与结果之间的关系。
4. 本关相对上一关增加了什么发现、决定或可复用成果。

重点处理“点几下却不知道为什么通过”“重复操作但没有新发现”“会做但被界面拖住”这三类体验。

### 5.2 各类关卡的审阅重点

下表给出检查方向，不限定具体改版方案；可根据实际试玩替换代表关卡。

| 关卡类型 | 值得重点解决的问题 |
| --- | --- |
| NOT与早期组合电路 | 基本操作是否自然；从接线教程过渡到独立构建时，是否存在认知断层；规格和反馈是否帮助思考 |
| 锁存器、寄存器、RAM与CPU | 能否看清状态变化、控制与数据的关系；复用自己的成果是否有意义；复杂连接是否被界面放大成负担 |
| 系统性能与缓存局部性 | 能否看清改了什么、哪些条件没变、为何结果不同；不仅给出更快或更慢的数字 |
| 缓冲、预取与数据布局 | 结构、排程和访问方式如何影响结果是否直观；失败是否提供下一次尝试的依据 |
| 表示、服务与地址预测 | 多个目标和成本能否被理解；玩家是否知道当前在改方案还是查看旧记录 |
| 内容压缩、内容预测 | 能否区分还原、比较、预测与揭晓；样例、规则和实际输出的关系是否清楚 |
| 创造与保存 | 玩家能否带着自己的意图改变结果，选择并保存作品；观看旧作品、再生成和继续编辑是否容易区分 |

### 5.3 可以主动改进的范围

- 关内信息顺序、操作节奏、示例和图解的呈现、反馈定位、工具开放时机与非强制帮助。
- 重复阅读、反复开窗、重复准备和无意义确认等流程负担。
- 关键成果的可视化、复用提示，以及不同阶段之间的承接。

如果发现问题根源在正式任务要求、难度安排或解锁关系，可以提出小范围调整建议，说明收益与影响。涉及正式判定、模拟规则和存档的变更单独确认，不为改善文案而悄悄改变玩法。

**完成效果：** 玩家主要在决定“怎样让系统工作或变好”，而不是猜测“界面希望我点什么”。

## 6. 引导：准确、有用、适时退场

现有引导条、规格表、操作演示和状态反馈应当作为基础继续完善，不再并行增加另一套教程。[S1][S5]

- 基本操作可以明确示范；解谜策略则提供观察方向和分级帮助，保留自主发现的空间。
- 引导要对应真实状态：尚未连接、连接未完整、未运行、结果不符、已通过、待封装或保存，应有不同回应。
- 操作演示应与当前控件、端口和布局一致，容易暂停、结束或重新查看，不替玩家完成任务。
- 失败反馈指出可检查的实际差异；成功反馈说明本次完成了什么，以及下一步可做什么。
- 熟悉的动作不要反复强制教学；玩家主动探索时，引导应让出空间。
- 详细原理可按需阅读，但必要规格、关键动作和当前错误不能只能靠悬停或长手册才能发现。

**完成效果：** 玩家不必先读完长篇说明才能开始，也不会因为帮助被简化而失去必要信息。

## 7. 壹与叙事：有角色感，但不挤占玩法

本轮以已有故事、罗同学的成片与确认稿为依据，集中完善关键节点，不重新改写全部世界观。

- 保持壹温和、克制、愿意帮助玩家独立理解的角色方向，让它不只是冷淡的任务播报器。
- 在首次进入、重要发现和保存作品等节点，让壹表达动机、关注与回应；不要每关都附上一段人生评价。
- 技术结果由真实运行支撑，角色语言可以有温度，但不替玩家宣告未发生的理解或必然的性能收益。
- 关内提示、章末对话、档案与CG各有作用，避免同一个故事被重复讲述。
- 统一文字输出节奏与停顿；操作信息即时可读。既有I／1形图形是文字尾随光标，不据此另立壹的头像或实体形象。
- 保留“从构建到理解局限，再到自主创造”的联系，不把每条计算规律硬套成人生寓言。

**完成效果：** 玩家能感到壹在陪伴和回应自己的行动，而不是一边操作、一边被不断要求阅读。

## 8. CG、过渡与声音：验收已接入的完整旅程

两段CG已经接入：开场后进入实验室，首次正式完成序章最后的LOAD/STORE后播放第二段，再接原通关流程。已有跳过、观看记录与旧档处理。[S4]

本轮重点：

- 检查影片与实验室的空间、明暗、终端位置及气质是否连贯；以实际成片和当前场景为准精修衔接。
- 检查影片结束后玩家是否知道下一步，以及是否还要重复经过不必要的介绍或进入动画。
- 检查正常播放、跳过、暂停恢复和返回后的操作权与焦点，不因表现优化改变既有进度。
- 检查清晰度、黑边、全屏、音量和音画同步；终端过渡与常用操作的动效应适度，不反复拖慢操作。
- 精修必要的按钮、接线、运行和成果反馈音，保持轻柔、统一；静音时仍能理解状态。

**完成效果：** CG不只是一个能播放的附件，而是自然进入实际游戏、回到实际操作的一部分。

## 9. 推进方式与展示材料配合

### 第一阶段：确认实际效果，选出本轮最重要的问题

先核对当前版本和可用素材，按现有运行授权检查真实画面与操作。结合主创和同学反馈，形成一份短清单，区分已经改善、仍需修改和需要主创决定的事项。不要把旧报告中的待办直接视为当前缺陷。

### 第二阶段：做出一组完整样板，再推广

优先完成一段入门构建、一段性能或数据优化、一段后期创造的可玩改进。先让视觉、引导、操作与结果在同一段体验中成立，再推广共性规则到其他工作台。代表关卡由实际问题决定，不必拘泥于固定列表。

### 第三阶段：全局统一与版本收尾

检查各章节入口、返回、求助、运行和保存；修复跨场景不一致与新回归，补齐CG与音频验收。最终成果是一版可连续游玩的游戏，而不是几个单独漂亮的页面。

### PPT与视频并行

展示材料不等待全部开发结束。尽早提供可用的实机截图与连续操作录屏；对还会变化的元件、首页和工作台标出需要替换的镜头。临近交付时稳定这些页面，只替换实际有变化的素材，不重新改变整条宣传片结构。

录屏应展示真实目标、玩家操作、运行结果和获得的成果。只读演示、测试模式与实际玩家操作应区分，不用演示替代真实通关。

### 团队成果的使用

陈同学的元件与视觉方案、常同学的UI反馈、刘同学的教学稿、罗同学的CG和故事、苏同学的展示需求，都是本轮输入。结合已确认方向取用；有冲突时集中说明，不要求主创逐个决定像素和按钮。

如果Codex已完成新元件或其他接入，Claude从该成果继续精修，不另起竞争实现；同一工作区的开发与运行按已有协作约定交接。

## 10. 最终交付与必要边界

### 交付

1. **可运行候选版本**，说明提交身份与本轮实际变化。
2. **同场景前后对照**，覆盖实验室、元件、典型工作台和后期页面；不以参考图冒充实际效果。
3. **连续操作录屏**，至少展示一段完整的开始、尝试、反馈、完成或保存过程，并提供宣传片可用镜头。
4. **简短交接**，写清已完成、尚有问题、需主创决定，以及PPT／视频哪些素材应更新。

在相关测试之外，重点走通：进入关卡、操作、求助与关闭、失败与修改、通过与封装／保存、返回与重启。使用实际导出包检查媒体和操作；测试通过与真人理解分别记录。遵守现有开窗／运行约定，尚未实际观察的项目明确留待验收。

### 边界

- 最新主创要求优先于旧讨论；同学初稿与旧候选故事不自动成为定稿。
- 可以主动重排局部UI、精修视觉、改善关内节奏，不局限于换颜色和补文字。
- 保留真实端口、模拟结果、正式完成判定、玩家作品与存档，以及游戏／测试模式隔离；影响这些内容的修改另行说明。
