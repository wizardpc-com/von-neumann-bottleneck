## 1. 存的必须是可重放输入

最小持久单位是 **模型版本 + 完整公开任务 + 完整可编辑方案 + 本地名称**。保存时真实运行，载入后重新计算，成绩及 Trace 不从文件恢复为权威结果。文件中的名字、列表位置、创建时间也不参与计算条件。

建议区分三种身份：

1. `condition_id` 继续由 `Model.condition_id(task)` 产生：它已包含数据、查询顺序/重复/索引、到达规则、空间上限、模型与内存成本。只在此身份相同的行间比较。
2. `plan_id` 继续由 `Model.plan_id(plan)` 产生：用于确认当前结果是否仍对应有效方案。它刻意忽略 `copy_mode=none` 时暂未生效的复制选择。
3. 已保存项目的本地 ID/规范输入摘要只负责寻址、重试及导入去重；不能替代前两项，也不能作为结果真实性的证明。

必须保留完整方案中的暂未生效设置。按有效 `plan_id` 合并相同榜单行可以避免重复成绩，但不能因此静默覆盖玩家有不同复制设置或名称的草稿。

建议保存最多 **8 个完整条件、每条件 8 个命名方案、全档不超过 64 个方案和 1MiB**；这些是可调整的首版产品上限。与现有每条件 24 次临时运行历史分开。命名作品满额时显式替换/删除，不能沿用临时历史的自动淘汰而丢掉长期作品。保存失败保留待保存输入，精确重试，不提前宣称成功。

启动时只验证结构和边界；选中条件后最多重算该条件的 8 个方案。排序只重排已获得的同批结果，编辑不触发全档重算。持久档不包含全部事件、输出和地图；它们在查看/运行所选方案时产生，避免把 64 份最大 Trace 同时恢复进内存。

## 2. 新负载首先改变条件索引，不能复用场景桶

当前 `session.gd:10-27` 以四个 `task_id` 作为状态键，并由 `Model.scenario(task_id)` 提供真实任务。若允许 17/32/64 条记录、8/16 请求、不同索引或空间预算，继续沿用这个键会让同名模板的草稿、比较基准和历史互相覆盖。

最小调整是：Session 持有经过验证且分离的完整任务快照；状态以完整 `condition_id` 寻址。选择模板只是创建/选中一个条件，已有作品按自己的实际任务重开，不能用当前模板数据替代旧数据。保留基础模板 ID 并不代表负载相同，第四轮额外 16 请求探针已经证明这个区别。

当前模型允许的合法上限足够支持首版变化：64 条四字段记录、8 个查询描述、16 份逻辑请求、4096 个查询值/输出、32768 个保守事件上限（`model.gd:224-263`）。生成器无需先修改模拟成本；把生成的完整任务放入胶囊即可。若采用 seed，必须同时固定生成器版本，且存下完整任务；不要只存“今天/随机种子”并依赖今后的生成算法重建。

字段/索引顺序不能为去重而排序。重复索引和非单调索引具有实际语义。后续若对玩家开放任意索引，必须重新检查 `lab.gd:324-327`“单份查询没有切块收益，因此禁用记录块”的 UI 假设：当前内层按 tile 遍历，而 tile 内按原索引顺序消费；对非单调重复索引，组大小 1 时 tile 也可能改变执行顺序。当前四份固定工作负载不触发此扩展边界。

同一个模板 ID 可以被合法任务内容改变为另一个到达规则；因此导入预览必须显示实际 `task.release`、请求、记录和空间上限，不能只凭 `scan_batch` 这样的名字推断条件。

## 3. 实验分享与挑战应有独立协议

推荐独立前缀，如 `VNBS1:`，不扩充或借壳 `VNB4C1`。一个精简的首版重放信封可包含：

```text
v, model, condition, task, plan, objective
```

`task` 是完整正规化任务，`plan` 是完整正规化可编辑方案。`objective` 仅使用已实现的枚举；如果本轮只做方案保存，可以先省掉此字段，避免预先冻结未选择的挑战规则。不要传入分数、排名、`passed`、有效成绩、文件路径、资源路径、脚本或可执行表达式。

导入顺序应是：

1. UTF-8 字节限制、版本/前缀、严格 JSON/规范表示检查。
2. 逐层精确字段和数值/数组上限验证；禁止未知字段被正规化吞掉。
3. 当前模型匹配，重新计算完整条件，并核对信封条件。
4. 调用公开 `Model.evaluate(task,plan)`；检查完整正确结果、无执行错误、预期输出一致及返回身份。
5. 仅显示本次实测指标与条件摘要；预览不改变草稿、当前基准或档案。
6. 显式采用时再次核对原码/原上下文，创建或打开这个完整条件；恢复方案为一次可撤销编辑。

如果允许约束目标，“同条件”仍指模拟条件；**挑战规则身份另外绑定目标指标和约束**。相同负载下 `总周期更少、Q1 不超过某上限` 与无 Q1 上限不应混成同一挑战榜。阈值是公开规则，不是可信成绩；基准数字从目标方案重算，不从信封自报读取。

目标层建议由策略审计确定。首版足以支持“选择一份正确实测方案 → 指定独立指标 → 改进并重测”，保留四项差值。若加响应/空间约束，明确它是玩家制定的公开条件或从另一份实测锚点得到；不要做加权综合分，不把所有四项均不差作为默认唯一赢法。对于已经在有限样本前沿的目标，后者可能没有可找到的改进。0B 空间也不能被暗示为可以继续严格降低。

导入字节上限不能照搬正式挑战的 4096B。按当前源码上限构造的 64 记录、8 查询、16 请求、4096 查询/输出值信封，Python 规范 JSON 估算已达 **4435B**，保守事件数 **25891**。这只是静态序列化估算，没有调用 Godot，也不是最终协议验收。建议新码先限 **8192B**，并由 Godot 对最大合法边界做实际编码/解码和运行测试；若最终字段导致不足再明确增加，不截断内容。

保持正式协议的严格规范表示方式，可拒绝重复键、未知嵌套字段及浮点拼写差异。字节限先于解析，结构/计数限先于模拟。任何异常返回失败且不修改会话。没有必要接受压缩包、磁盘路径或外部资源。

## 4. 旧模型、未知档案与实际写盘

建议保持以下三态，不把“不兼容”误显示成“没有作品”：

| 情形 | 行为 |
| --- | --- |
| 支持的信封/存储格式，当前模型和条件匹配 | 本机复测后可比较/挑战。 |
| 支持格式，但模型或条件身份不匹配 | 原码原字节保留，可导出，标记不兼容；不排名，不静默改模型字段再运行。 |
| 未知 schema、未知嵌套字段、损坏、超限、无效 UTF-8、读失败 | 整档只读，原文件不覆盖；允许继续临时探索和复制当前方案码。 |

“旧条件”需区分：文件内完整任务保持不变，而当前预设模板改了，不应自动使其消失；它仍可在支持的模型下作为独立的历史完整条件重新执行。只有身份校验不一致或模型不受支持才是不可比较。若要按新规则重算旧作品，显式复制为新项目，保留原输入及旧身份。

复用现有 Store 的提交顺序：检查原盘摘要 → 验证全部待存快照 → 写同目录临时文件并检查 flush/error → 再检查原盘 → 原子替换 → 仅成功后提交内存状态。无变化请求也必须先做外部修改检查。新增/重命名/删除失败均保留已提交内存和原字节；未提交请求可以明确重试。

成功写 `.tmp` 并不等于已保存；未完成替换的临时文件不能在重启时自动“恢复”为权威记录。原子替换主要保证不留下半份目标文件，不应表述为突然断电下所有平台的持久性保证。建议先保留这个简单契约，通过崩溃阶段和异常注入验证，不引入多副本自动合并。

**固定实验配置新增了同时启动两个进程的实际风险。** 当前 Store 的固定 `.tmp` 加前后摘要检查没有互斥：它不能保证两个并发提交之间的原子 compare-and-swap，也可能让两个进程共用临时路径。首版应明确单写者并在实验存储层或稳定启动入口拒绝第二个写者；每次提交用自己拥有的临时文件。若采用可原子建立的锁目录/锁文件，崩溃遗留锁须进入可解释的只读恢复流程，不能仅凭时间自动删除另一进程的锁。不要为此声称现有正式 Store 已有多进程保证，也不要无授权扩展修改它。

## 5. 固定实验配置是可玩交付的一部分

`scripts/run-experiment.py:22-27` 当前拒绝 `layout_strategy --profile`；`:32-35,50-59` 每次创建 UUID 项目和全新 `VonNeumannBottleneckChecks/experiments/<stamp>` 数据目录。仅添加 `user://portfolio.json` 不能让玩家下次运行同一命令找回作品。

建议为本实验单独允许一个短 ASCII 名称的稳定配置，保留新建 QA 项目，但把数据目录固定到：

```text
VonNeumannBottleneckChecks/layout_strategy/<safe-profile>
```

当前 `lab.gd:55-65` 的隔离检查允许这个命名空间；不必放宽到普通玩家目录。不要直接复用现有 `primary=service` 分支、添加 `--candidate-save` 或 `--candidate-journey`，它们属于其它实验的整合路线。普通验证仍使用唯一 QA 配置；给玩家的预览命令/启动器明确使用同一个实验配置。

持久化范围应在界面说清楚：命名作品及挑战已保存；24 次临时运行、未保存草稿及 Undo 是否跨进程保留必须与实际实现一致。若只做命名作品保存，退出保护仍需检查未保存草稿，不能因档案写入成功就移除整个退出提醒。断开或回退新实验时不删这个侧文件；旧代码忽略它，不影响正式关卡和旧成绩。

最小可玩的验收路线：固定实验配置启动 → 运行两份真正有取舍的方案 → 保存命名作品 → 退出并再次用相同配置启动 → 重新测量并显示原指标/身份 → 设为目标 → 修改并运行 → 与同条件目标比较 → 恢复另一作品并一次撤销。导入另一个条件只新增/切换自己的条件，原草稿和基准可以完整返回。

## 6. 线上可信性的下一步只需要清楚的接口边界

当前 `server/community.py:29-44` 验证的是客户端上传的两组阶段/流量/空间数字及现有正式规则；`:87-106` 选择每个安装的最小自报总周期，固定返回 `verified: false`。`server/feedback_server.py:77` 调用这层校验，未调用 Godot 或方案重放。它明确没有提供实验重放权威，不能复用为“已验证实验榜”。

新离线胶囊带完整任务和方案，已能为未来固定版本重放提供必要输入。未来服务端若建设验证，应由白名单模型实现、固定完整条件和公开挑战规则重跑输入，自己生成输出、指标、条件/方案/Trace 身份。客户端 Trace hash 只能作为一致性对照，不能作为免重放证明。公开竞争还需服务器固定允许的挑战条件，否则各人任意设计负载的成绩没有横向意义。

本轮不需要更新 `community_rules.json`、开放 HTTP、上传、账号、认证、防作弊声明或部署。用同一个纯实验模型和明确的胶囊契约完成本地进程间复算，是最小且可检验的推进。

## 决定性测试与交接条件

- **条件/方案身份：** 同模板但数据、索引、请求重复、到达规则、空间任一变化不得混榜；相同正规化输入跨 JSON、字典顺序和语言保持身份；暂未生效设置留在草稿但不制造新有效成绩。
- **真实运行：** 保留第四轮原四工作负载和旧正式规范 Trace 验证；分享/保存/重启后复算必须核对输出、Q1、完整响应序列、总周期、流量、空间与 Trace。分配失败/未完成响应不能成为低分获胜者。
- **恶意/损坏输入：** 超字节、深层错误类型、重复键、未知字段、额外成绩、非法/非有限数字、重复复制字段、索引范围、请求数/事件数超限；预览失败不改变草稿/基准/档案。
- **持久保护：** 读/open/短读/UTF-8/目录、临时文件写失败、真实 rename 失败、外部改写/出现/删除、未知版本和嵌套损坏；原字节与已提交内存不变，原请求可重试。崩溃临时文件不自动授予成绩。
- **容量与同名：** 逐层/总量边界、已保存作品不被临时历史淘汰、同名/相同有效方案但不同暂存设置、旧码与新码共存；整个快照验证后才覆盖。
- **两进程：** 同固定配置重启成功；第二个并发写者被拒绝或明确只读；不同配置完全隔离。子进程/QA 不读取正式玩家目录。
- **界面：** 导入预览不变更，采用行为可预期，原条件草稿可返回；保存失败/已保存/仅会话有效三个状态清晰；语言/F10/F8/退出保护嵌套保持已有输入约束和最小窗口可达性。
- **可回退：** 新文件/前缀只属于实验；关闭实验入口后正式 60 项、`layout-memory-1`、既有 `VNB4C1` 和玩家成果仍通过原回归，无自动迁移或清理用户侧文件。

主线程冻结计划时最需要确定的产品选择是：保存单位和容量、固定实验配置入口、是否本轮分享码、是否有约束目标，以及并发写者处理。上述建议不改变正式模拟规则，不需要废除旧成果；新增实验存档与协议应在版本化计划中写明再实现。
