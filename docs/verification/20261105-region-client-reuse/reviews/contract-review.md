## Why a single completed service is a valid candidate

`Base.run()` in `experiments/representation/plan_model.gd:75–147` reads only the submitted data, plan and machine/address fields. It creates a new Trace, typed data copy, deterministic encoded blocks and a fresh decoded cache on each call (`96–97`). Codec encoding/decoding has no clock, randomness, external state or asynchronous yield. Cache contents and LRU state are local; `configure()` clears state, `put()` copies its input, `fetch()` returns a new typed array, and `snapshot()` copies keys/LRU/sizes. Base does not read a client-specific input or mutate the caller's arrays/plan.

Region invokes Base once before preparation validation, and the current later-client calls use exactly the same spec/plan. The wrapper reads the completed service after setting only its test_name; it does not mutate its cache snapshots or events. Online preparation reads copied block evidence and writes into the new Region Trace. Therefore using the same completed cold-service evidence for later clients preserves the computed cold history under the current synchronous, same-input contract. It does not mean sharing a live cache across clients.

This reasoning does not extend to future per-client requests/machines, shared client state, random behavior, callbacks or concurrent mutation of input. None of those semantics is being added in Round12. Existing arbitrary Object/cyclic provenance behavior must not be redefined or represented as newly isolated by this optimization.
